# R01 · Room FTS4 中文分词调研（ICU 与二元切分）

> 日期：2026-11-27（Asia/Shanghai）
> 基线：Android `origin/main` `f18915f00b501c547f9920fde2fd8fbf779c1fdd`（INF-00 已合入）
> 类型：只读调研；本文不修改业务代码。结论在真机/模拟器矩阵验证前不得标 `DEVICE_TESTED`。
> 敏感路径口径：开发机目录一律写 `<campus-root>`。

## 1. 一页结论（当前草案）

1. **不建议把 Room FTS4 `tokenize=icu` 当作唯一、默认的中文分词实现。**AOSP API 31–36 的参考构建证据显示 Android target 的 SQLite 编译了 FTS4 且启用 ICU；但 Room 官方 API 文档明确提示 ICU tokenizer「Not available in certain Android builds (e.g. vendor)」。应用分发对象是 OEM Android 12–16 真机，不是仅限 AOSP 参考镜像，因此无法把它当成可移植契约。
2. **推荐默认方案：写入时做 Unicode 规范化与中文重叠二元切分，把人工 token 流写入 FTS4；查询时执行同一套改写。**这样不依赖设备 SQLite 编译选项，行为可单元测试、可复现，也避开 Android 无法注册自定义 C tokenizer 的限制。
3. **ICU 可作为后续可选增强，不作为首版路径。**若未来要启用 ICU fast path，必须先有设备能力探测、索引格式版本和完整重建/迁移策略；否则同一数据库在不同设备间备份恢复后会出现分词语义不一致。
4. **证据等级当前为 B/C，不是 A 级真机证据。**开发机无可用模拟器：用户组不含 kvm，且 `<campus-root>/android-sdk` 无 emulator 与 system-images；只能采用 Robolectric/静态构件/文献证据。

## 3. 待补证据明细

- AOSP API 31–36 SQLite build flags 对照。
- Room 官方 `FtsOptions.TOKENIZER_ICU` 限制原文。
- SQLite ICU tokenizer 语义与 ICU 中文词典分词能力。
- Robolectric 4.17 native runtime 是否包含/可用 ICU tokenizer。
- 二元切分索引大小估算与查询改写规则。
- W1-03 验收词「高数」「离散」「W111」测试矩阵。

## 4. 当前推荐草案

- `search_docs` 保存原始展示文本、规范化文本和生成 token 流；`search_fts` 只承担倒排索引，优先评估 external-content 模式以避免重复存储。
- 写入 token 流时：ASCII/数字小写化，全角转半角，标点折叠为空格，中文连续段生成重叠 bigram；英文/数字保留整词。
- 查询时复用同一 normalizer；中文查询改写为 bigram 的 AND/phrase 组合，短查询、混合查询和 prefix 查询单列规则。
