# R01 · Room FTS4 中文分词调研（ICU 与二元切分）

> 日期：2026-11-27（Asia/Shanghai）
> 基线：Android origin/main f18915f00b501c547f9920fde2fd8fbf779c1fdd（INF-00 已合入）
> 类型：只读调研；本文不修改业务代码。所有结论在真机/模拟器矩阵验证前不得标 DEVICE_TESTED 或 SCHOOL_VERIFIED。
> 敏感路径口径：开发机目录一律写 <campus-root>；Robolectric 探针只注入开发机构建 worktree，未进入仓库 diff。

## 1. 一页结论

1. **不能把 Room FTS4 tokenize=icu 当作 API 31–36 上可无条件依赖的默认中文分词。**AOSP release tag 证据显示 API 31–36 的 Android target SQLite 都启用 FTS4 与 ICU，libandroid_runtime 也链接 libsqlite；Robolectric NATIVE SQLite 在 API 31–35 实测可创建 tokenize=icu 表。但 Room 官方 FtsOptions 文档明确写 TOKENIZER_ICU “Not available in certain Android builds (e.g. vendor)”。SQLite 官方也把 ICU tokenizer 定义为编译期可选。面向 OEM 真机时，这不是公开、稳定、可迁移的能力契约。
2. **推荐首版默认：写入时做 Unicode 规范化 + 中文重叠二元切分，把生成 token 流交给 FTS4 unicode61；查询时执行同一套改写。**该路径只依赖 SQLite 内置 FTS4/unicode61，不依赖 ICU 编译选项，不需要 Android 暴露不了的自定义 C tokenizer，也能在 JVM/Robolectric 中确定测试。
3. **即使使用 ICU，高数 ≠ 高等数学 的问题仍存在。**本次 Robolectric probe 中，ICU 对 高等数学A（一） 查询 高等数学=命中、数学=命中，但 高数=0。W1-03 验收词“高数”必须通过 SearchIndexContributor 的 aliases/别名扩展解决，不能指望 ICU 或 bigram 自然命中。
4. **推荐 schema 方向：search_docs 存原文、规范化文本与 token 流；search_fts 用 FTS4 external-content 模式引用 token 流。**SQLite 官方说明 external/contentless FTS 可显著节省空间；本次 host 模拟显示 regular FTS 因重复存 token 流，增量约为 external 的 3.2–3.6 倍。
5. **证据等级：B/C，不是 A。**开发机当前无可用模拟器：用户不在 kvm 组，<campus-root>/android-sdk 中 emulator 与 system-images 均 absent。因此不能宣称 API 31–36 真机可靠；只能给出 AOSP/Robolectric/文献证据和必须复测的矩阵。

## 4. ICU 可用性证据

### 4.1 AOSP release tag 对照（证据 B）

| API | Android | 代表 tag | SQLite FTS4 | Android target ICU | vendor/product 变体 |
|---:|---|---|---|---|---|
| 31 | 12 | android-12.0.0_r1 | -DSQLITE_ENABLE_FTS4 | -DSQLITE_ENABLE_ICU + libandroidicu | vendor 明确 -USQLITE_ENABLE_ICU 并排除 libandroidicu |
| 32 | 12L | android-12.1.0_r1 | 同上 | 同上 | 同上 |
| 33 | 13 | android-13.0.0_r1 | 同上 | 同上 | vendor 禁用；另有 noicu 静态变体 |
| 34 | 14 | android-14.0.0_r1 | 同上 | 同上 | vendor 禁用；另有 noicu 静态变体 |
| 35 | 15 | android-15.0.0_r1 | 同上 | 同上 | vendor 禁用；另有 noicu 静态变体；该 tag 未给出 product 禁用证据 |
| 36 | 16 | android-16.0.0_r1 | 同上 | 同上 | product/vendor 禁用；另有 noicu 静态变体 |

关键源码事实：

- external/sqlite/dist/Android.bp 的公共 flags 含 SQLITE_ENABLE_FTS3、SQLITE_ENABLE_FTS3_BACKWARDS、SQLITE_ENABLE_FTS4。
- 同一文件 target.android 分支链接 libandroidicu 且定义 SQLITE_ENABLE_ICU；API 31–35 的 target.vendor 反向 undefine 并排除 libandroidicu；API 36 的 target.product 与 target.vendor 均反向 undefine 并排除 libandroidicu。
- frameworks/base/core/jni/Android.bp 中 libandroid_runtime 的 android target 链接 libsqlite；因此 AOSP 手机系统镜像上的 android.database.sqlite 路径确能到达这份 SQLite。
- 这些只证明 **AOSP 参考构建**，不证明每个 OEM/定制 Android build 都把同一能力暴露给第三方 App。

### 4.2 Room 与 SQLite 官方语义（证据 B）

- Room FtsOptions 文档列出 TOKENIZER_ICU，并明确写：**Not available in certain Android builds (e.g. vendor)**。这是本调研最重要的否决性证据：Room 本身不把 ICU 当可移植能力。
- Room Fts4 文档只说明 tokenizer 与 tokenizerArgs 会用于 FTS table；Room 不附带 ICU 实现，也不兜底创建失败。
- SQLite FTS 文档说明：只有 C ICU library 可用且编译时定义 SQLITE_ENABLE_ICU，才会存在名为 icu 的内置 tokenizer；ICU tokenizer 按 ICU word-boundary 规则切词，只丢弃全空白 token，不做 stemming 或复杂标点处理。
- SQLite 文档还说明 unicode61 自 SQLite 3.7.13 起内置；unicode61 做 Unicode case folding，并用 Unicode 空格/标点分隔 token。
- ICU 官方 Boundary Analysis 文档说明中文、日文、泰文等无空格语言会使用 dictionary-based BreakIterator；中文/日文共用带词频的统一词典并用动态规划选择更可能的切分。这说明 ICU 的中文分词质量理论上优于朴素 bigram，但不改变可用性与别名命中问题。
- SQLite 自定义 tokenizer 需要 C 层 sqlite3_tokenizer_module 指针注册；Android Room/Java API 没有暴露该注册能力，因此不能把“自写 C tokenizer”当作现实备选。

## 5. 可靠性裁决

1. **“能用”**：在 AOSP 参考构建与 Robolectric NATIVE 的 API 31–35 中，tokenize=icu 能创建并工作。
2. **“可靠默认可移植”**：否。理由按权重排序：Room 官方明确警告某些 Android build 不可用；SQLite ICU 是编译期可选；OEM/裁剪构建变体不在应用可控制范围内；数据库备份/迁移跨设备后不能假设同一 tokenizer 语义。
3. **运行时探测不是充分解法**：数据库迁移执行 CREATE VIRTUAL TABLE 时若设备缺 ICU，失败点已经太晚；即使 catch 后重建，也要处理已有索引、备份恢复、版本标记和多设备语义差异。首版不应把用户数据迁移押在不可移植编译选项上。
4. **质量层面 ICU 也非充分条件**：它能用词典分中文词，但 probe 已证明缩略别名“高数”仍不命中； alias 层无论选哪条路都必须做。

## 6. 推荐方案：写入时二元切分 + FTS4 unicode61

### 6.1 索引文档模型

- search_docs：权威文档表，保存 docId、entityType、entityId、profileId、title/body/code/aliases 原文、normalizedText、tokenStream、updatedAt、deleted。
- search_fts：FTS4 虚表，external-content 指向 search_docs 的 token 列；不为 snippet 使用 FTS 原文，展示与高亮从 search_docs 原文/规范化文本重新计算。
- 推荐分列 tokenStreamTitle、tokenStreamBody、tokenStreamCode、tokenStreamAlias，至少逻辑上区分 title/code/alias/body 权重；若 Room external-content + trigger 对多列实现复杂，可首版先单 tokenStream，再用 search_docs 字段做二级排序。
- 所有写入仍走 EntityWriter/SearchIndexContributor；删除或撤销变更时同事务删除/重建对应 doc，禁止只删原实体留下 FTS 幽灵结果。

### 6.2 规范化规则

写入与查询必须使用同一个纯 Kotlin SearchTextNormalizer，禁止两边漂移：

1. Unicode NFKC；ASCII 大写用 Locale.ROOT 小写化；全角字母数字按 NFKC 结果折叠。
2. 去除零宽字符、控制字符和不可见格式符；把空白、标点、括号、连接符统一折叠为单个空格。
3. 不做中文繁简转换、不猜测拼音、不做词义纠错；这些属于 alias/数据包能力，不塞进 tokenizer。
4. 中文/日文/韩文表意文字连续段生成重叠 bigram；段长 1 时保留单字到 fallback/unigram 通道。
5. ASCII letter/digit/underscore 连续段保留为整词并小写化；W111 → w111，F01 → f01，MATH101 → math101。
6. 别名只写入 tokenStreamAlias，不污染正文；alias 必须经过同一规范化。

示例：高等数学A（一） 的正文 bigram 流近似为“高等 等数 数学 a 一”；若 contributor 提供别名“高数”，alias 流包含“高数”。

### 6.3 查询改写规则

1. 输入先同一 normalizer；空查询不发 MATCH，返回空或按最近文档浏览态处理。
2. 用户输入一律按字面量处理，不开放 FTS 操作符语法；OR/AND/NOT/NEAR、引号、星号、减号都只是普通字符或被分隔符折叠，避免注入 FTS 语法。
3. 按空白/标点切出独立查询单元，单元之间用显式 AND。
4. 纯中文单元长度 ≥2：生成重叠 bigram，并用 FTS phrase 保持顺序。例如 高等数学 → "高等 等数 数学"；离散 → "离散"；数学 → "数学"。
5. 单中文字符：不要求 bigram MATCH；走 search_docs.normalizedText 的 LIKE/instr fallback 或独立 unigram 列。语料规模小时 fallback 可接受，且避免 *字符* 前缀造成的错配。
6. 纯 ASCII/数字单元：小写化后 exact MATCH；若长度 ≥3 且位于查询末尾，可附加原生 prefix 形式（例如 w11*）。FTS prefix 只用于 ASCII，不对中文 bigram 加星号。
7. 混合单元先拆 script run；跨单元仍 AND。示例“莲花街 W111”→ phrase(莲花 花街) AND w111。
8. 别名命中和正文命中合并去重；排序建议 title > alias > code > body，再用 bm25/matchinfo 或二级 SQL 权重微调。首版宁可简单确定，不要为排名引入不可解释分数。

### 6.4 别名策略是验收硬要求

- “离散”是“离散数学”的连续 bigram，可自然命中；“W111”大小写规范化后可自然命中。
- “高数”不是“高等数学”的连续子串，ICU probe 也不命中；必须由 contributor 写入 alias token。
- 初始 alias 来源优先级：数据包/学校目录显式别名 > 用户确认别名 > 领域规则表 > 保守生成规则。
- 课程首版可维护可审查缩写表：高等数学→高数、线性代数→线代、大学英语→大英、大学物理→大物、概率论与数理统计→概率/概率统计、马克思主义基本原理→马原、中国近现代史纲要→史纲。该表属于领域数据，不属于通用 tokenizer；每条必须有测试。
- 不建议首期自动生成任意跳字二元组（如 高数、离数）作为通用 token：索引膨胀且误伤高。若未来要支持模糊缩略，应单独评估排名与容量。

## 7. 索引大小估算（证据 C）

方法：开发机 host Python sqlite 3.46.1，内存库，page_size 4096；确定性合成文档（每篇约 70 个汉字 + 5 个 ASCII 词），写入后 optimize。该模型只用于数量级估算，不代表 Android/page layout/真实语料。

| 文档数 | tokens | FTS 形式 | FTS 增量 | 折合每篇增量 |
|---:|---:|---|---:|---:|
| 1,000 | 74,000 | external-content | 256 KiB | 262 B |
| 1,000 | 74,000 | regular FTS | 832 KiB | 852 B |
| 2,000 | 148,000 | external-content | 492 KiB | 252 B |
| 2,000 | 148,000 | regular FTS | 1,640 KiB | 840 B |
| 5,000 | 370,000 | external-content | 1,096 KiB | 225 B |
| 5,000 | 370,000 | regular FTS | 3,968 KiB | 813 B |

解释与规划值：

- 合成语料原文约 254 B/篇、token 流约 512 B/篇；external FTS 倒排增量约 225–262 B/篇。regular FTS 额外复制 token 流，导致增量约 3.2–3.6 倍。
- SQLite 官方说明 documents 通常大于 full-text index，content= external/contentless 可显著节省空间；FTS4 相对 FTS3 的额外开销通常 1–2%，小文档可到 10%。
- 对校园个人数据量级，按 2,000 篇估算 external FTS 倒排约 0.5 MiB；5,000 篇约 1.1 MiB。即使按 3 倍不确定性预留，也低于 4 MiB，不是主要包体/存储风险。真正成本是 tokenStream 本身与写入/重建事务，必须通过 external-content 和批量重建控制。
- 真实语料词项更分散时倒排会变大；上述数字不可作为承诺。W1-03 必须用真实导出夹具重新量 dbstat/page_count。

## 8. W1-03 推荐落地顺序

1. 先实现纯 Kotlin SearchTextNormalizer/BigramTokenizer/QueryRewriter；不碰 Room schema，用单元测试冻结 token 流。
2. 再实现 SearchIndexContributor 注册与 alias 提供机制；课程、成绩、考试、personal_events、campus graph 各自声明可索引字段。
3. Room v12 新建 search_docs 与 external-content search_fts；迁移只在事务内建空索引并异步/分批 rebuild，避免升级时长时间锁库。
4. 重建完整性：rebuild 后比较 search_docs count、search_fts docid count、抽样 docid； corruption 时允许整表重建，不允许幽灵 docid。
5. 不启用 ICU fast path。若未来重开该决策，先完成 API 31–36 真机 matrix、OEM 样本、备份跨设备迁移设计和索引版本化。
