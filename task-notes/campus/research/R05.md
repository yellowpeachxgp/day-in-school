## 0. 结论摘要

1. CampusRepository.kt 当前 **8920 行**，直接公开实例方法 **164 个**；另有 **32 个公开 Flow**、9 个公开标量/回调属性、7 个 internal 生命周期/修复方法、1 个 companion getInstance。方法表已逐个覆盖，无一遗漏。
2. 目标方法分布极不均衡：**102/164（62.2%）**不属于课表、学期、成绩、考试、Moments、擦除或同步的窄义领域。若把计划中的 CampusServicesRepository 当成普通大类文件，它仍会超过 1500 行门禁；因此 W0-05 必须把它实现为**薄协调 Repository + 内部业务分片**，而不是第二个巨型文件。
3. 8 个 W0-05 目标本身不足以表达全部长期架构边界。本报告仍把每个方法映射到计划内目标，但在 CampusServicesRepository 下标出 8 个内部落点：AppPreferencesStore、ReminderSettingsStore、UtilityService、LibrarySeatService、CloudIdentityService、CampusContentService、ParcelHubService、ExtensionPluginRegistry。后续应另开卡把其中若干提升为独立 Repository / Port。
4. UI 侧五个 feature 的巨型文件普遍直接在 Composable 中收集 Repository Flow、持有表单/对话框状态、发协程、访问 WebView/Intent/Clipboard/权限/Coordinator。W0-06 的关键不是“复制粘贴成更多文件”，而是按 MASTER_PLAN §10.2 把 **Route（副作用与导航）/ ViewModel（状态聚合与动作）/ state（不可变契约）/ ui（纯渲染）/ preview（状态矩阵）** 分开。
5. 最高风险不变量：课表恢复命令的 mutationToken 原子语义（CampusRepository.kt:797–805、1973–2054）、考试学期来源证据与禁止猜测（2990–3002、内部修复 926 起）、云身份 generation/ABA 守卫（5228–5305）、云抢座价格漂移重确认（189–216）、擦除链路的 hook 与世代屏障（290–304、5093–5188）。这些必须先补特征测试再搬移。

## 5. 建议搬迁批次（供 W0-05 / W0-06 使用，不代表已实施）

### 5.1 CampusRepository（W0-05）

1. **批次 0：特征测试与类型外壳**。先固化 164 个方法的输入输出快照，尤其 occurrence 命令、考试修复、擦除、云身份 generation、价格漂移；建立 8 个目标类和 deprecated facade 空委托。
2. **批次 1：Term + Grades + Exam**。小、边界清晰；把学期 rollover、节次补齐、考试修复 audit 一起迁，避免半搬状态。
3. **批次 2：Timetable**。先搬只读快照/Flow，再搬课程编辑，最后搬 occurrence 命令；upsertOccurrenceOverrideStamped 与通知只能在单一写入口。
4. **批次 3：Moments**。帖子、教材、防丢牌可独立迁移；viewer 集合与云登录态重置必须保持。
5. **批次 4：CampusServices 内部 shard**。按 AppPreferencesStore → ReminderSettingsStore → UtilityService → ParcelHubService → CampusContentService/ExtensionPluginRegistry → CloudIdentityService → LibrarySeatService 顺序；后两类锁与世代最多，最后搬。
6. **批次 5：SyncOrchestrator**。在领域写入口稳定后迁移教务同步和云同步；applyLiveSyncData 只编排，不复制领域逻辑。
7. **批次 6：ProfileDataWiper**。最后迁移并逐项断言课程、成绩、考试、提醒、水电、专注、云身份、预约、包裹、插件、DataStore key 与 secure vault 均清零；before-wipe hook 顺序要有回归测试。

### 5.2 巨型 Screen（W0-06a/b/c）
