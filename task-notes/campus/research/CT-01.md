## 1. planned/reserved 生命周期

- CT-01 的 11 个群组/邀请/成员端点是 **planned**，不是 D2 论坛/私信的 reserved/501。
- OpenAPI 每个 planned operation 显式携带 `x-dis-status: planned`；endpoint inventory 携带机器可读 `status: planned` 与 `contract_card: CT-01`。
- parity/validator 将 active 与 planned/reserved 分开：97 个 active core 仍要求 runtime/inventory/OpenAPI 100% 双向一致；planned 不计入 runtime 缺失，但如果 runtime 提前出现未登记 active 路由仍失败。
- W4 实现卡必须把对应端点从 planned 翻成 active，并在同一 PR 提供运行时路由；不允许先实现 shadow route。

## 2. CT-01 领域决策

1. 群组类型固定为 `study / dorm / club / project`；`school_id` 是隔离边界，创建请求与列表查询显式携带，其他端点通过组资源校验同一学校作用域。
2. 群主角色为 `OWNER / ADMIN / MEMBER`；`memberId` 是成员关系 UUID，不直接暴露或推导其他学校身份。
3. 邀请码有过期时间与次数上限；QR 载荷格式为 `dis-group-invite:v1:<code>`。
4. 所有写操作要求 `Idempotency-Key`；创建类重复提交返回原结果的 200 replay，更新/删除重复提交返回幂等 ack/current state。
5. `sharing_level` 只表达忙闲共享级别，首期最高为 `BUSY_BLOCKS_30MIN`；时间块细节留给 CT-02。退出、被移除或群组归档立即撤回共享。
6. `group.member.joined` 覆盖创建者入组与接受邀请；`group.member.left` 覆盖主动退出、被移除与群组归档。事件 key 幂等。
