## 问题与真实入口

`LibrarySeatBookingScreen.kt` 的初次组合 `remember { LocalDate.now(...) }` 负责摘要和两类查询，而持久 submitter 的 paramsProvider 又在点击时重新读取时钟。23:59 选择明天后跨到 00:00，前者仍是原日期，后者变成后一天；上轮修复闭包捕获并未消除这两套来源。

本轮使用生产页面实际持有的 `LibraryBookingDateState` 统一绝对日期、查询状态和选座；显示、计划预览、草稿、双引擎提交与立即选座均从该状态读取。`LibraryBookingPlanSubmitter` 仍是实际创建入口，测试以假端口记录它交给仓库的不可变快照。

- 今天/明天自动跟随上海日期。前台每秒核验，恢复前台、查询前后、身份挂起返回后和每次提交/确认再次核验；更新可观察日期后立即清空旧区域、座位和待确认报价，再触发新日期查询。
- 指定日期保存为绝对年月日；跨午夜不改变。指定日期已过去则拒绝提交，等待用户选择。
- 查询响应绑定日期修订号和请求序号；过期、乱序或日期/区域不符的结果不能覆盖新页面。
- 点击瞬间发现跨日先拒绝本次操作，等待新查询结果。旧报价确认、挂起身份读取期间改参、日期往返编辑以及过期报价均拒绝；不会拿旧确认执行新参数。
- 立即选座在登录挂起前冻结日期和座位，恢复后复核完整上下文，再调用学校适配器。日期不在后台重新换算。

## 回归与检查

先补跨午夜失败回归，再修复并扩展。`LibraryBookingDateStateTest` 使用可注入 Clock，覆盖今天/明天/手动日期、前台/恢复共用核验入口、区域和座位查询在途跨日、晚到报价、报价弹窗跨日、日期/时间编辑和往返、明确日期过期及报价过期，分别覆盖本机与云端的实际 submitter 入口；没有将自建日期变量当成 UI 接线验证。

跨端 `reservation-quote-envelope.json` 和 `reservation-error-envelopes.json` 都来自 Cloud 实际 handler 生成器；Android 用原始 body 验证单位、版本、金额、身份、时间和错误响应。报价接口失败必须零写，`STORAGE_COMMIT_UNKNOWN` 创建响应必须保留为 ResponseAmbiguous，不自动换键创建。原有仓库引擎交接在无法核实云端停止时继续保留 RESULT_UNKNOWN。

CI 新增固定 Cloud 提交的 checkout、handler 契约测试和 fixture 字节相等检查，源提交见 `tools/contract-ci/cloud-fixture-source.json`。Cloud fixture 变更必须通过生成器同步，不能分别手写两个 mock。

完整检查按仓库 CI 执行全部 JVM/Android 单元测试、Debug/Release Lint、Debug/未签名 Release APK 构建、Room schema 未变检查及契约检查。首次全量单测虽成功，但发现桌面图标测试启动真实 Application，异步账号数据库任务越过 Robolectric 沙箱销毁；已将该 PackageManager 单元测试的 Application 隔离，保留原断言并重测。最终测试数量、静态分析、构建与远端 CI 结果见交付记录。

未执行真机/模拟器 Compose 点击、真实学校账号或真实跨午夜设备实验。状态持有者与实际提交入口的 JVM 回归不等价于这些验收。

补查学校适配器发现此前还将未来日期换成今天查询、将总座位数当空位数并把未来座位统一设为空闲。已在 Day 与 Cloud 同时取消这些回退，学校请求时间窗始终绑定传入绝对日期，保留学校真实可用状态。默认时段返回错误日期时也只归一到目标日期；未开放目标日期查询则明确失败，不能将其他日期的布局伪装成目标日期空闲。这意味着学校未开放未来日期查询时，页面须等待学校开放后才能选座建草稿；真实学校兼容性尚未验证。新增实际传输端口回归，并贯通状态持有者、真实适配器查询和双引擎 submitter。

## 数据与回滚

Room schema/version 不变，无数据库迁移、无生产数据写入。现有计划的绝对日期不重写；日期选择只影响新草稿。新的日期选择状态是页面临时/Saveable 状态，指定日期不会转换成相对天数。

旧客户端仍可使用 Cloud 原报价单位与版本 token；新 Cloud 对未知存储返回 503，当前 Day 会保留不确定性而不会伪造创建成功。没有引入自动真实扣退款。

Day 代码可回退而不回滚 Room 数据；回退会重新引入跨午夜缺陷。不要为了撤销客户端代码而删除/恢复旧计划表。Cloud 的 intent、回执、资金核验及禁止未知状态降级规则见 Cloud 同名复核文档；两个仓库必须分别遵守其数据恢复边界。
