# core:ledger 记账语义

`:core:ledger` 是纯 JVM 模块，只表达“账本如何记录”，不执行支付、转账、冻结、扣款或退款。任何后续云端实现都必须复用本文规则，避免客户端与云端因舍入或排序不同产生金额分歧。

## 金额

- `Money` 使用 signed `Long` 表示“分”（fen），禁止使用浮点数。
- 加减与取负做溢出检查；超出 signed 64-bit 范围即失败，不允许环绕。
- 负金额只表示冲正/退款方向的账记录，不表示支付已经完成。

## 参与人标识

参与人 ID 与结算 ID 是跨端同步的 opaque id，不是展示名。标识符只接受非空、无空白/control 字符的可打印 ASCII（代码点 33..126）。因此 ASCII 字典序在 JVM 与云端常见语言中一致。

## 分摊算法

支持四种规则：

1. `SplitRule.Equal`：群体全部成员均摊。
2. `SplitRule.Selected`：只在显式指定的参与人之间均摊；指定人必须是群体成员。
3. `SplitRule.Ratios`：按整数比例分摊；未列出的成员权重为零。
4. `SplitRule.StayDays`：按入住天数分摊；未列出的成员入住天数为零。

权重/天数必须非负；只有严格大于零的成员是有效参与人。群体为空、成员重复、指定未知成员、权重/天数为负、没有任何有效参与人都会以稳定错误码失败。

## 固定余数规则

所有非零金额使用“最大余数法”：

1. 对每个有效参与人计算精确有理数份额：总金额 × 权重 ÷ 权重和。
2. 先取该有理数的 floor 作为基础份额。
3. 未分完的金额只可能是若干个 1 分单位；按 fractional remainder 从大到小，每人最多补 1 分。
4. fractional remainder 相同时，参与人 ID 字典序较小者优先。
5. 输出按参与人 ID 字典序升序排列；输出不依赖成员或 Map 的输入顺序。
6. 零金额不产生余数，但保留有效参与人的零金额行，便于解释账。
7. 负金额先对其绝对值执行同一规则，再给所有份额加负号；因此正负两个方向都严格满足“份额总和 = 原金额”。

例子：10 分在 ASCII ID 为 a、b、c 的三人中等额分摊，余数完全相同，所以 a 得 4 分，b 与 c 各得 3 分。

中间乘法和权重和使用任意精度整数计算；最终份额仍必须能表示为 signed 64-bit 分。由于份额总和守恒且原金额本身是 `Long`，正常输入不会因中间乘法溢出而静默出错。

## 两方确认结算状态机

`Settlement` 是一条记账型结清记录，金额必须严格为正，debtor 与 creditor 必须不同。

- 初始：`PENDING_BOTH_CONFIRMATIONS`。
- debtor 确认后：等待 creditor，即 `PENDING_CREDITOR_CONFIRMATION`。
- creditor 确认后：等待 debtor，即 `PENDING_DEBTOR_CONFIRMATION`。
- 两方都确认后：终态 `SETTLED`。
- 完成前任一方可取消：终态 `CANCELLED`。
- 同一方重复确认是幂等空操作； outsider 不能确认或取消；终态后不能继续变更。

`SETTLED` 仅表示双方认可账本已结清，不是支付成功证明。真实资金是否流动不属于本模块语义；若未来接入支付，必须由独立模块/事件显式记录，不能改写本状态含义。
